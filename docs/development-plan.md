## PR 본문 작성 규칙

한 Issue를 한 PR로 제출한다. 브랜치는 `feat/<담당코드>-<작업>`처럼 만들고 PR의 대상 브랜치는 `main`으로 둔다. PR 본문에는 아래 다섯 가지를 적는다. **“완료했습니다”만 적지 않는다.**

1. **연결 Issue와 목적:** `[F2-02] / #10`처럼 코드와 실제 Issue 번호를 함께 쓰고, 사용자가 무엇을 할 수 있게 됐는지 한두 문장으로 설명한다.
2. **변경 범위:** 주요 파일·화면·DB 테이블·API 경로와 바뀐 동작을 적는다. 공통 파일이나 계약을 바꿨다면 그 이유와 영향받는 담당자를 적는다.
3. **데이터 상태와 의존성:** mock·가상 데이터인지, Supabase에 실제 저장되는지 분명히 쓴다. 아직 연결되지 않은 API와 선행 Issue를 적는다.
4. **검증 방법과 결과:** 실행한 명령(예: `cd web && npm run lint`, `npm run build`)과 브라우저에서 직접 확인한 정상·실패·빈 상태를 적는다. 화면 작업이면 스크린샷이나 짧은 시연 방법을 넣는다.
5. **리뷰 요청:** 리뷰어가 집중해서 볼 부분과 남은 문제를 적는다. 비밀 키나 실제 개인정보를 PR 본문·캡처에 넣지 않는다.

예시: `관련 Issue: [F2-02] / #10` → `변경: 인계 목록과 상세 화면` → `데이터: mock, 실제 연결은 #26 머지 후 #11에서 진행` → `검증: npm run lint/build 통과, 모바일 빈 목록 확인` → `리뷰 요청: 상태 이름이 #25 계약과 같은지 확인`.

## 교차 리뷰와 완료 기준

**프론트엔드와 백엔드가 서로의 PR을 검토한다.** F1 정재헌의 PR은 B1 이은규, B1의 PR은 F1이 리뷰한다. F2 문수혁의 PR은 B2 하이칼, B2의 PR은 F2가 리뷰한다. 리뷰어는 코드뿐 아니라 요청·응답 형식, 버튼·화면 동작, 권한과 실패 흐름까지 본다. 같은 직무 팀원의 추가 검토는 가능하지만 지정된 교차 리뷰를 대신하지 않는다.

수요일·일요일 마감은 **담당자의 구현·자체 검증·PR 제출과 교차 리뷰어의 피드백 반영·승인까지**를 뜻한다. 정재헌이 그 뒤 승인된 PR을 최종 merge한다. Issue는 다음 조건을 모두 만족하면 닫는다.

- Issue 본문에 적힌 기능과 완료 기준을 실제로 확인했다. mock 범위의 Issue라면 mock이라고 명확히 표시했고, 실제 연결을 완료했다고 주장하지 않는다.
- PR 본문에 변경 사항·검증 결과·남은 의존성을 적었고, 지정된 프론트엔드·백엔드 교차 리뷰어가 승인했다.
- 정재헌이 `main`에 merge한 뒤 실행·빌드 또는 해당 사용자 흐름을 다시 확인했다. 배포가 필요한 Issue는 배포 사이트에서도 확인한다.

PR을 열거나 코드를 푸시한 것만으로 Issue를 완료 처리하지 않는다. 리뷰에서 수정 요청이 나오면 같은 PR에서 고치고 다시 검토받는다.

현재 익명 사용자의 기록은 작성한 브라우저 계정에서만 조회된다. 팀 공동 조회/운영에는 인증과 소속·역할 정책이 필요하다. 실제 어르신 데이터를 입력하지 말고 개발용 가상 데이터만 사용한다.
