`web/src/types/`, `web/src/components/`, `web/src/lib/mock/`, 패키지 설정, 루트 레이아웃은 공통 파일이다. 변경 전 Issue 댓글로 영향받는 팀원과 합의하고 가능하면 별도 PR로 먼저 반영한다. 프론트엔드는 고정된 API 예시로 UI를 먼저 만들고, 백엔드는 같은 계약으로 DB·API를 병행한다. 실제 연결은 선행 PR이 `main`에 merge된 후 통합 Issue에서 한다.

각 작업은 최신 `main`에서 별도 브랜치를 만든다. 다른 PR이 merge되면 작업 브랜치에 최신 `main`을 반영하고 다시 빌드한다. 텍스트 충돌이 없어도 타입·응답·권한이 맞지 않으면 통합 실패로 본다.

## PR 본문 규칙

한 Issue를 한 PR로 제출하고 base는 `main`, compare는 개인 작업 브랜치로 둔다. 본문에는 아래 내용을 빠짐없이 적는다.

```md
## 관련 Issue와 목적
Closes #[실제 Issue 번호]
[담당코드] 사용자가 할 수 있게 된 일을 설명

## 변경 내용
- 바뀐 화면·파일·DB·API

## 데이터와 의존성
- 실제 Supabase / mock / 가상 데이터 여부
- 아직 필요한 선행 Issue

## 검증 결과
- npm run lint
- npm run build
- 확인한 정상·빈 상태·실패·모바일 흐름

## 리뷰 요청
- 리뷰어가 집중해서 확인할 부분
- 알려진 제한 또는 남은 문제
```

비밀 키와 실제 개인정보는 PR·Issue·스크린샷에 넣지 않는다.

## Issue·PR 완료 기준

다음 항목을 모두 만족해야 Issue를 닫는다.

- Issue 범위와 완료 기준을 실제로 확인했다.
- `lint`와 `build`가 통과하고 담당자가 브라우저에서 직접 확인했다.
- 실제 데이터와 mock을 명확히 구분했다.
- 지정된 프론트엔드·백엔드 교차 리뷰어가 승인했다.
- 정재헌이 `main`에 merge한 뒤 Production 핵심 흐름을 다시 확인했다.
- 검증 결과와 남은 제한을 Issue 댓글에 남겼다.

코드를 푸시하거나 PR을 연 것만으로는 완료가 아니다. 리뷰 수정 요청은 같은 PR에서 반영하고 다시 승인을 받는다.
