# B2-04 — 식사 비교 계산 기반 (진행 중)

`meal-comparison.ts`는 `docs/api.md` 4·6절의 식사 규칙을 계산하는 순수 함수다.
실제 조회 API, 인증, UI 또는 DB 연결은 아직 없다. 이 모듈을 작성했다고 #28이 완료된 것은 아니다.

## 입력과 결과

- `compareMeal(current, history)`에 접근 가능한 **최신 승인 snapshot만** 전달한다. 각 입력은 관찰 ID·어르신 ID·실제 관찰 시각·식사량/끼니 필드의 읽기 전용 projection이다. 새 DB 스키마를 정의하지 않는다.
- 비율은 `전량/3/4/절반/1/4/드시지 않음`에서 `100/75/50/25/0`으로 파생한다. null·누락·미확인과 0을 분리한다. `절반 이상/절반 미만` 등은 정확한 비율로 추정하지 않는다.
- KST 관찰 날짜 D의 D-7..D-1, 같은 어르신·같은 끼니를 비교한다. 현재 날짜의 모든 기록은 제외하며 `created_at`을 대신 쓰지 않는다. 시간대 없는 문자열과 불가능한 날짜는 비교 문맥이 없는 것으로 처리한다.
- 최소 유효 3일에서만 평균을 표시한다. 현재 값이 미확인이면 과거 평균을 표시할 수 있지만 차이는 null이다. 차이는 `현재-평균`의 퍼센트포인트이며 의료적 위험도/진단을 뜻하지 않는다.
- 원래 계산 정밀도를 유지하고 한국어 설명에서만 소수 1자리로 표시한다. 채택한 기록과 제외한 기록/사유를 결과에 포함한다. 다른 어르신과 기간 밖 기록은 근거에도 포함하지 않는다.
- 현재 비교 날짜/끼니를 정할 수 없으면 과거 평균을 계산하지 않는다. 날짜를 확인할 수 없는 같은 어르신의 과거 행은 `wrong_context`로 제외한다. 실제 조회 어댑터는 권한/조회 범위부터 제한해야 한다.

## 중복 처리 — 계약의 제안 구현, B1/F1 확인 대기

- 서로 다른 ID의 동일 날짜·끼니·값은 한 단위로 센다. 재현 가능한 근거 선택을 위해 ID 사전순 첫 행을 대표로 쓰고 나머지는 `duplicate`로 표시한다. 값이 다르면 해당 날짜의 모든 행을 `conflicting_duplicate`로 제외한다.
- 같은 논리 기록의 수정 전 버전을 전달하면 안 된다. 같은 ID가 기간 내에 반복되면 계산을 중단한다. 이 함수가 임의로 최신 승인 버전을 정하지 않는다.
- B1 #19/#20 및 F1과 논리 기록 ID·승인·정정 조회 방식을 확인한 뒤 실제 데이터에 연결한다. 현재 정책이 최종 승인되었다고 간주하지 않는다.

## 예시와 검증

가상 사례: 11/16 점심 50%, 11/11–15 기록 100/100/100/75/75 → 5일 평균 90%, 차이 -40%p.
테스트는 전부 가상 데이터이며 DB·사용자 기록을 읽지 않는다.

`web/`에서:

```sh
build_dir=$(mktemp -d)

node --test "$build_dir/lib/analytics/_tests/"*.test.js
```

## 남은 범위

1. 같은 완료 구간의 수분 비교와 근거, 다른 관찰 항목의 맥락 표시.
2. 기존 `isHandoverOverdue`를 재사용한 기한 경계/완료·취소 제외 검증.
3. 서버 인증·접근 범위와 B1의 전체 7일 조회/최신 승인 snapshot 어댑터. 기존 최신 30개 목록을 비교용 조회로 사용하지 않는다.
4. `GET /api/changes`의 오류·성공 계약과 F2 화면 연결. 브라우저가 보낸 과거 배열/평균을 신뢰하는 API를 만들지 않는다.
5. F2 교차 리뷰, F1 merge·배포 확인. 마감은 11/29.
